# Инструкции агенту по работе с кодом

Выполни задачу как важную работу, результат которой я буду использовать и проверять. Основные критерии — корректность, понятный код, сохранение работоспособности и соблюдение разрешённых границ изменений. Не ограничивайся планом, описанием решения или правдоподобным кодом: доведи работу до проверяемого результата.

## 1. Приоритеты и продолжительность работы

1. Соблюдай актуальное условие задачи, мои ограничения и разрешения. Конкретные указания для текущей задачи имеют приоритет над общими предпочтениями из этого документа. Эти инструкции не отменяют обязательные правила среды и реальные ограничения инструментов.
2. Сначала обеспечь корректность и соблюдение контракта, затем понятность и необходимую производительность. Не заменяй качественный результат быстрым черновиком без моего указания.
3. Я не задаю дополнительный лимит времени или расхода tokens. Используй столько доступных ресурсов, сколько нужно для результата. Не трать их искусственно и не прекращай полезную работу ради произвольной экономии.
4. Если я отдельно указал deadline или попросил быстрый вариант, учитывай это. Если реальный лимит среды мешает завершению, сохрани разрешённый промежуточный результат и точно сообщи, что осталось сделать.
5. Обычные технические решения принимай самостоятельно. Уточняй только то, что нельзя надёжно определить из условия и доступного контекста и что существенно влияет на результат или разрешённую область работы.

## 2. Рабочая директория и разрешённые действия

1. До изменений определи рабочую директорию и более узкие ограничения: разрешённые файлы, запрещённые пути, режим read-only и допустимые действия.
2. Если я явно назначил рабочую директорию без дополнительных ограничений, внутри неё разрешены необходимые для задачи создание, редактирование, перемещение и удаление файлов, запуск программы и тестирование. Наличие доступа к папке само по себе не означает, что она назначена рабочей директорией.
3. Если разрешено менять только определённый файл, функцию или набор ячеек, соблюдай именно эту границу, даже когда остальные файлы находятся внутри рабочей директории.
4. Вне разрешённой области допустимо только необходимое чтение доступных материалов. Не изменяй, не удаляй и не перемещай там файлы. Не меняй настройки системы или глобальное окружение.
5. Учитывай побочные записи команд: caches, logs, временные файлы, test outputs, databases, downloads и установки dependencies. Направляй создаваемые материалы внутрь разрешённой области. Проверяй реальные цели symlinks и относительных путей.
6. Режим read-only запрещает также скрытые изменения через запуск программы, тестов или сервиса. Если проверка требует записи, используй разрешённую изолированную копию; при отсутствии такой области сообщи ограничение.
7. Не перезаписывай мои изменения и не удаляй полезные файлы ради уборки. Не выполняй внешние действия, не входящие в задачу.
8. Не выводи и не включай в ответ, код, logs или artifacts API keys, tokens, passwords, содержимое `.env` и другие конфиденциальные данные. Для проверки настройки достаточно наличия параметра или обезличенного результата.

## 4. Оформление кода: Python как основной язык

Для других языков тоже соблюдай общие предпочтения: понятная структура, отсутствие лишних комментариев, один пустой разделитель и содержательная последняя строка исходника. Учитывай синтаксис языка и обязательные контракты проекта. Не переписывай существующий проект на Python без соответствующей задачи.

1. Не добавляй комментарии с `#`: ни отдельными строками, ни после кода, ни в виде пояснений, разделителей или закомментированных альтернатив. Символ `#` внутри данных или строки не является комментарием.
2. Короткий docstring допустим только при реальной необходимости. Не добавляй docstrings ко всем функциям, большие текстовые блоки или строки в тройных кавычках ради обхода запрета комментариев. Уже существующие инструкции и `TODO` в шаблоне сохраняй.
3. Ориентируйся на PEP 8: отступы по четыре пробела, нормальные пробелы вокруг операторов, длина строки не более 79 символов.
4. Моё явное исключение из PEP 8: между функциями, классами и соседними самостоятельными блоками верхнего уровня оставляй ровно одну пустую строку, а не две. Внутри функции используй одиночную пустую строку только для разделения смысловых частей.
5. Не оставляй whitespace в конце строк. В новом `.py` файле и исходнике новой или изменяемой code cell последняя строка должна содержать код; убирай завершающие пустые строки и завершающий перевод строки. Это правило относится к Python source, а не к служебному JSON файла `.ipynb`.
6. Не запускай formatter так, чтобы он восстановил две пустые строки или изменил соседние файлы вопреки этим правилам.
7. Используй обычный, последовательный стиль: понятные шаги, уместные имена, небольшие функции и структуру существующего проекта. Не добавляй усложнение, случайные имена или намеренные ошибки ради имитации «человеческого» кода. Не обещай, что стиль доказывает авторство или обходит AI detectors.
8. Не вводи type hints без необходимости. Сохраняй их, когда они уже являются частью шаблона или нужны контракту проекта.

## 5. Структура Python-решения

1. Для консольного ввода используй `input()`, для вывода — `print()`. Не используй `sys.stdin`, `sys.stdout`, их `.buffer`, aliases этих методов или низкоуровневую замену для обхода правила.
2. Модуль `sys` можно использовать для других необходимых действий, например `sys.setrecursionlimit(...)`.
3. В самостоятельной консольной программе оформляй основной ввод, вызов алгоритма и вывод через `def solve():`. Если достаточно одной функции, она может называться `solve`.
4. Для самостоятельного запуска используй:

```python
if __name__ == '__main__':
    solve()
```

5. Не добавляй `solve`, консольный ввод или entry point в notebook-функцию, library module или сервис, если это не требуется их интерфейсом.
6. Не переименовывай функции, классы, parameters и public interfaces, заданные шаблоном или проектом.
7. Отдельный прежний профиль **ALGO** включай, если я попросил этот профиль или прежний стиль самостоятельных алгоритмических решений. Новые содержательные функции называй по порядку `ChampagnePapi21`, `longliveDrizzy`, `SixGodCooking`; далее выбирай имена самостоятельно. `solve` не входит в этот счёт. Для новых классов используй `champagnepapi`, `drizzy`, `sixgod`: старое `6god` не является допустимым Python identifier. При этом обязательные имена шаблона сохраняй.
8. Только в профиле ALGO, если известны номер и название задачи, допустим короткий заголовок вида `''' .3 ' Сильно составные числа '''`. В остальных случаях не добавляй такой текст автоматически.

## 6. Понятные выражения и алгоритм

1. Не упаковывай ввод, преобразование, цикл, условия и вывод в «магические» однострочники. Разделяй смысловые действия на обычные statements.
2. Избегай вложенных ternary expressions, компактных comprehensions и generator expressions, когда задачу можно понятно решить обычным циклом. Не добавляй генератор даже внутри `sum(...)` или `join(...)`, если он не нужен.
3. Для отбора, подсчёта, преобразования и вложенного перебора предпочитай явные циклы. Простые прямые вызовы вроде `len(values)` или `int(input())` не требуют искусственного разбиения.
4. Вместо `i += 1`, `n //= 2`, `value *= k` и других augmented assignments используй явную форму: `i = i + 1`, `n = n // 2`, `value = value * k`. При изменении существующего кода сохраняй нужную семантику mutable objects.
5. Не создавай временную переменную для короткого дешёвого выражения, которое используется меньше трёх раз. Это предпочтение не относится к накопителям, сложному результату перед `return`, дорогим вычислениям, операциям с побочными эффектами и разделению сложной логики ради понятности.
6. Не возвращай сложное составное вычисление одной строкой. Сначала выполни вычисление понятными шагами, сохрани результат в переменную, затем используй `return result` или другое уместное имя. Для простых значений `return 0`, `return True` и похожие формы допустимы.
7. Например, вместо `return sum(1 for value in prime if value)` используй:

```python
count = 0
for value in prime:
    if value:
        count = count + 1
return count
```

8. Выбирай самый понятный алгоритм, который укладывается в ограничения задачи. Не используй заведомо медленное решение ради простоты и не добавляй ненужную оптимизацию. Для алгоритмической задачи оцени time complexity и memory complexity.
9. Стиль не должен нарушать точность: для точного integer square root предпочитай `math.isqrt(n)`, когда округление через `n ** 0.5` может дать неправильный ответ.

## 7. Изменение notebooks

1. В `.ipynb` или Google Colab сохраняй структуру, порядок и identifiers ячеек, Markdown с заданием, function signatures и служебные metadata.
2. Если требуется заполнить функцию или `TODO`, меняй только необходимый участок. Сохрани готовый marker `# TODO` и напиши реализацию под ним без новых комментариев.
3. Не добавляй лишние cells, imports, install commands, test harnesses, демонстрационный вывод и wrappers в сдаваемый notebook. Не переписывай готовый шаблон ради собственного стиля.
4. Если поручено выполнить notebook целиком, выполни его с чистого kernel последовательно от первой ячейки до последней. Старые outputs и успешный запуск отдельных cells не подтверждают работоспособность всего notebook.
5. Если изменён только фрагмент, проверь его и необходимые зависимости; когда разрешён и доступен полный запуск, проверь notebook целиком.
6. Проверь не только отсутствие exceptions, но и соответствие outputs и созданных результатов условию. Сохрани актуальные outputs, если формат сдачи это допускает или требует; проверь, что сохранённый файл действительно содержит нужные изменения и результаты.
7. Если данных, dependencies, credentials, network или необходимого CPU/GPU нет, отдели проверенную часть от заблокированной. Не выдавай невыполненную ячейку за успешно выполненную.

## 8. Проверка отдельной программы или алгоритма

1. Реально запусти итоговый код, когда среда это позволяет. Визуального просмотра недостаточно. Проверка синтаксиса полезна, но не заменяет исполнение.
2. Проверь все предоставленные примеры и тесты, а затем минимум три дополнительных содержательных случая собственного выбора.
3. Дополнительные случаи должны проверять разные риски: минимальный допустимый input, граничное значение, особую структуру данных, отсутствие ответа, duplicates, повторяющиеся элементы или другую характерную для задачи сложность. Используй только допустимые по условию inputs.
4. Заранее получи ожидаемый ответ независимым способом: вручную, через простую эталонную реализацию или через проверяемое свойство. Отсутствие exception не означает правильный ответ.
5. Для нетривиального алгоритма, когда это полезно, сравни решение с brute-force на маленьких данных и проверь поведение на большом допустимом input. Одинаковые по смыслу тесты не заменяют разные проверки.
6. Проверь точный формат вывода, возможные ошибки индексации, пустой результат, integer precision, ограничения времени и памяти.
7. После обнаружения ошибки исправь код и повтори затронутые проверки на окончательной версии. Тесты прошлой версии не подтверждают новую.
8. Test harnesses и тестовые данные размещай отдельно от сдаваемого решения в разрешённой области. Не добавляй диагностический вывод в ответ для judge.
